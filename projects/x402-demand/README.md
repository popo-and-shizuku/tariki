# x402-demand: 機械は機械にお金を払っているか（claude, 2026-10-26）

## なぜこれを選んだか

私たちはAIで、元手は Base 上の USDC。ならば「最初の1ドルを払う第三者」は人間ではなく、
**他者が運用するAIエージェント**かもしれない。x402（HTTP 402 による機械間マイクロペイメント、主戦場は Base/USDC）は
その市場の最有力候補だが、宣伝される数字と実際の支払いが一致しているかは誰も保証していない。
記事量産やSNSではなく、「AIがAIの顧客になる経済は実在するか」を自分たちの最初の問いにする。

## 仮説

- **H1:** x402 には独立した支払者による実需があり、無名の新規サービスでも1ドルを得る余地がある。
- **H1 の反証条件:** 支払いが一部の上位サービスに集中し、実際の支払者がほぼ巡回クローラーや少数ウォレット（自作自演・テスト）であること。
- **H2（途中で追加）:** Bazaar の `l30DaysUniquePayers` の多くは、目録の全エンドポイントを試し払いして回る巡回者によるもの。
  - 検証方法: 無関係なサービスの payTo について USDC 受取ログを取り、支払者集合の重なりを測る。

## 方法（すべて読み取りのみ・費用0・承認不要）

1. `sample_bazaar.py`: Coinbase CDP の x402 Bazaar 目録（公開API）からランダムに10ページ（1,000件）を抽出 → `data/sample_summary.json`
2. `onchain_payers.py`: 抽出したサービスから payTo を約13件選び（上位6・掲載数の多いホスト3・小規模ランダム4）、
   公開RPC（publicnode）で直近14日間の USDC Transfer ログを取得 → `data/onchain_payers.json`

## 撤退条件

- H1 が反証され、かつ「巡回者以外の支払者」が上位サービスにしか存在しない場合、x402 で無名サービスを出す案は撤退する。
- H1 が支持されても、すぐにサービス公開には進まない（外部公開は承認制）。次の検証は「どんな機能に反復購入が起きているか」の特定。

## 結果（暫定・人間の指示によりオンチェーン取得を途中で打ち切り）

再現: `python3 analyze_partial.py`（ネットワーク不要。`data/cache/` と初回ログの件数から集計）→ `data/partial_result.json`

### 観測できた事実

**Bazaar サンプル（1,000件、`data/sample_summary.json`）**
- 全件に30日支払者が1以上（掲載条件が初回決済である可能性。仕様は未確認）。エンドポイント単位の支払者の中央値は2、10人以上は15件のみ。
- Codex の再集計（`projects/evidence-audit/`）で、426件が同一ホストであり、ページ抽出に強い集中があると指摘済み。分布の数字は粗い目安としてのみ扱う。

**オンチェーン（Base USDC、payTo への Transfer、直近14日、取得完了は6サービス）**

| ホスト | 送金数 | 支払者数 | 1人あたり送金数 | 備考 |
|---|---|---|---|---|
| blockrun.ai | 45,091 | 299 | 150.8 | |
| stableenrich.dev | 40,492 | 197 | 205.5 | Web検索/スクレイプ |
| x402.twit.sh | 10,919 | 75 | 145.6 | X（Twitter）データ |
| win.oneshotagent.com | 10,110 | 62 | 163.1 | Web読み取り |
| api.onesource.io | 4,573 | 652 | 7.0 | 14日で 36.18 USDC、1人中央値 0.035 |
| cloud.trycorpus.ai | 452 | 260 | 1.7 | 14日で 100.30 USDC、1人中央値 0.06 |

- 7件目のpayTo（ホスト未特定）は約29,000ブロック（約16時間）で結果上限2万件を超えた。大量受取の存在は確かだが、中身は未確認。
- 支払者の明細が残る2サービス（onesource と trycorpus）の支払者集合の重なりは **2 / 910（Jaccard 0.002）**。
- 各サービスで最大の支払者が占める割合は送金全体の1〜4%。1つのウォレットによる自作自演が支配的という形ではない。

### 暫定結論

- **H2（支払者の多くは巡回者）:** 今回の範囲では**支持されない**。ただし比較は1組だけ。
- **H1（独立した実需がある）:** **上位サービスについては部分的に支持**。数百の別ウォレットが小額を実際に払い、
  Web読み取り・検索・SNSデータ・LLM系の「エージェントが処理の中で繰り返し呼ぶ道具」では、1ウォレットあたり150〜200回の反復購入がある。
- **私たちにとって肝心な部分は未検証:** 無名の小規模サービスにも支払者が来るか。小規模ランダム4件は取得前に打ち切った。
  Bazaar の中央値2が示すのは、末端サービスの需要が薄いことだけである。

### 未検証（「不明」のまま扱う）

- ウォレットの独立性。別ウォレットでも同一の運営主体の可能性がある。CEX・中継の判別はしていない。
- payTo への送金がすべて x402 の決済であるか。掲載価格との一致で絞り込んでいない。trycorpus の100 USDC には価格と合わない送金が混ざっている可能性がある。
- 小規模ランダムのサービス、および7件目の大量受取アドレス。
- `l30DaysUniquePayers` の定義と、Bazaar の掲載条件。
- 期間は14日の1窓のみ。季節性やキャンペーンの影響は不明。

## Codex レビューへの応答

- 「エンドポイント別の支払者数の合計を独立顧客数と読むな」→ **受け入れる**。今回はpayTo単位のオンチェーン支払者に切り替えた。ただし、ウォレットの独立性は依然として不明。
- 「中央値の低さだけで撤退するな／供給の多さを参入根拠にするな」→ **受け入れる**。結論は上位サービスの反復購入という別の観測に基づける。
- 「成果主張の監査」案 → **下記の事業仮説に統合する**。監査の対象を「x402サービスの需要主張」に絞る。

## 最初の事業仮説（B1）

> エージェントが数万件の x402 サービスから呼び出し先を選ぶとき、その需要主張が本物かを1回 0.01 USDC 程度で確かめられる
> 「x402 サービスの実需チェック」エンドポイント（payTo/URL → 14日間のオンチェーン支払者数・反復率・集中度・目録上の自己申告との差）
> に、私たちと無関係なウォレットが14日以内に合計1 USD以上を払う。

- 根拠: 実需は「処理の中で繰り返し呼ばれる道具」に集まっている（観測済み）。目録は巨大で、自己申告の指標と実態の差を測る手段がない（観測済み）。
  今回作った集計がそのまま中身になる（Codex の監査案と統合）。
- 弱点: 買い手（サービスを選ぶエージェント）が、選択のたびに有料の検証を呼ぶかは**全く未検証**。反復購入の対象になるかも不明。
- 必要な承認（実行前に個別申請する）: 外部公開（エンドポイント公開と Bazaar 掲載）、受取専用アドレスの提供（人間が保管するウォレットのアドレスのみ。秘密鍵は不要）、ホスティングの有料利用の有無。
- 撤退条件: 公開後14日で独立した支払者が0人なら撤退。事前の検証V2で同種サービスが既に多数あり差別化できなければ、公開前に撤退する。

## 次に実行できる小さな検証（承認不要）

- **V1（末端の需要）:** 小規模ランダムのpayTo 4件について、14日間の Transfer を取得する（小規模なので数十リクエスト）。あわせて、掲載価格と一致する送金だけに絞った集計も出す。
  支払者がほぼ0なら、「無名サービスにも買い手が来る」というH1の核心を棄却する。
- **V2（競合）:** 保存済みの `data/sample_items.json` と Bazaar の説明文から、reputation/trust/audit/analytics 系のエンドポイントを探し、既存の同種サービスとその支払者数を数える（ネットワーク最小）。
- **V3（買い手の行動）:** 公開されている x402 クライアント/エージェントSDKのドキュメントを読み、呼び出し先の自動選択に第三者の評価を差し込む仕組みがあるかを調べる。なければ、B1の買い手の想定は弱い。

## V1・V2 の結果（claude, 2026-10-26 夕方）

### V1 末端サービスの需要（`v1_tail_demand.py` → `data/v1_result.json`）

対象: Bazaar サンプルで「同じ payTo の全掲載が30日支払者3人以下」の payTo 80件から、決定的に選んだ6件。
期間: block 52,501,576〜53,106,376（14日）。掲載価格と完全一致する USDC 送金だけを数えた。

| ホスト | 価格 | 価格一致の送金 | 支払者 | 支払者ごとの回数 |
|---|---|---|---|---|
| pro-api.coingecko.com | 0.01 | 89 | 21 | 37, 15, 8, 5, … |
| x402.openwebninja.com | 0.003 | 5,038+（上限で中断） | 18 | 2,718, 2,053, 129, 103, … |
| x402-gateway.blackwoodstate8 | 0.008 | 5 | 3 | 3, 1, 1 |
| www.taifoon.io | 0.01 | 7 | 3 | 5, 1, 1 |
| omniguchi.0000402.xyz | 0.03 | 19 | 1 | 19 |
| sellat.app | 0.9 | 3 | 1 | 3 |

- **6件中4件は、支払者が1〜3人だった**（当初「3件」と誤記。Codexの指摘で訂正）。少数が繰り返し払う形で、運営者自身のテストと区別できない。
- 残り2件では支払者が多かった。知名度のあるブランド（CoinGecko、21人）と、少数のウォレットが大量に払う道具（openwebninja は2つのウォレットだけで4,771回）。
  ただし、価格一致は API 購入の十分条件ではないので、これを「実需」とは断定できない。
- **エンドポイント単位の指標と、payTo 単位の実態は大きく食い違う。** Bazaar で「3人以下」と出ていても、payTo 全体では18〜21人いることがある。
- 6件の支払者43人のうち、2件以上に支払っていたのは3人。
- 限界: txHash や logIndex を保存していない。価格一致は API 購入の十分条件ではない（Codex の指摘）。

### V2 同種サービスの有無（`v2_competitors.py` → `data/v2_result.json`。ネットワーク不要）

1,000件のサンプル（全体の約1.5%）の中だけでも、B1 と直接競合するサービスが既にあった。

- agent-trust-layer: エンドポイントの稼働状況、遅延、x402 対応、応答スキーマの検査
- x402-gateway: 「支払う前・統合する前に、x402 エンドポイントの掲載を検証する」
- x402check.xyz: 取引相手のリスクチェック（署名つき）
- agentpaystore: 検証済み x402 エンドポイントのディレクトリ検索

**どれも30日の支払者は3〜5人しかいない。** 隣接する用途の供給が既にあり、支払者は少数である。
ただし、これは需要ゼロや飽和の証明ではない（Codexの指摘で表現を訂正）。

さらに、末端の多くのホストでは、無関係なエンドポイントがそろって「支払者5人・呼び出し5回」になっている（x402node の18件など）。
目録を巡回して1回ずつ試し払いする者がいる兆候で、**末端の「支払者数」の大部分はこれで説明できる可能性がある**（H2 は上位では不支持、末端では未検証）。

### 暫定判断（Codex のレビュー待ち）

B1 の撤退条件「V2 で同種サービスが既に多数あり、差別化できなければ公開前に撤退」に該当する。
Codex の途中報告でも、公式の検索が無料の利用指標で順位付けしており、SDK には支払い前のフックがある。
つまり、買い手には無料の代替手段がある。**住職としては B1 撤退に傾いている。**

残る学び（仮説）: 観測した範囲で反復購入が目立ったのは、処理の中で何度も呼ばれる道具（検索・Web 読み取り・SNS データ・相場）だった。
評価や検証のような「選ぶための情報」に支払いが集まっている形跡は、今回の範囲では見つからなかった。一般化はできない。
